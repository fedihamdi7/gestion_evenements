Projet « Gestion d'Événements » — Guide technique complet pour la validation

Architecture microservices — Spring Boot 3.5.14 · Spring Cloud 2025.0.2 · NestJS · Angular 21 · Keycloak 26 · RabbitMQ · Docker

1. Vue d'ensemble

L'application permet de gérer des événements : des utilisateurs s'inscrivent et se connectent (via Keycloak), consultent les événements, les réservent, laissent des avis (note + commentaire, uniquement s'ils ont réservé), et discutent en temps réel via une messagerie (Socket.IO). Le tout est découpé en microservices indépendants qui communiquent entre eux de façon synchrone (OpenFeign) et asynchrone (RabbitMQ), derrière un point d'entrée unique (API Gateway).

4. Les trois piliers d'infrastructure (à maîtriser parfaitement)

4.1 Config Server — la configuration centralisée

Problème résolu : avec 7 services, dupliquer les configs (URL de Keycloak, identifiants MySQL, adresse d'Eureka…) dans chaque module devient ingérable : une modification = 7 fichiers à changer.

Solution : un serveur Spring Cloud Config en mode native (il sert de simples fichiers, pas besoin de Git) : les fichiers sont dans config-server/src/main/resources/config/. Chaque service ne garde localement que 2 lignes : son spring.application.name et spring.config.import=configserver:http://localhost:8888. Au démarrage, le service appelle le config-server et reçoit « sa » config : le fichier partagé application.properties (hérité par tous : adresse Eureka, actuator) + son fichier propre (ex. service-avis.properties).

Point important : c'est pour ça que le config-server démarre en premier — sans lui, aucun service ne connaît ni sa base de données ni Eureka. Les valeurs utilisent des placeholders ${VAR:défaut} : en local le défaut (localhost) s'applique, dans Docker les variables d'environnement (ex. MYSQL_HOST=mysql) prennent le dessus — même code, deux environnements.

4.2 Eureka — la découverte de services

Problème résolu : la gateway doit router vers service-avis. Mais à quelle adresse ? En coder l'IP en dur casserait dès qu'on scale ou qu'on passe en Docker.

Solution : un annuaire. Au démarrage, chaque service s'enregistre dans Eureka sous son nom logique (SERVICE-AVIS…) avec son adresse, et envoie un heartbeat toutes les 30 s (sinon il est évincé de l'annuaire). Les clients (gateway, Feign) demandent à Eureka « qui est service-avis ? » et obtiennent l'adresse à jour. Le dashboard est visible sur http://localhost:8761 — à montrer pendant la démo.

Détail vu en TP : même le service NestJS (messaging) s'enregistre dans Eureka — via un petit client REST maison (eureka.ts) qui POST son inscription et renouvelle son heartbeat, preuve qu'Eureka est une simple API REST utilisable depuis n'importe quel langage.

4.3 API Gateway — le point d'entrée unique

Problème résolu : sans gateway, le frontend devrait connaître 5 ports différents, gérer le CORS 5 fois, et chaque service devrait re-vérifier la sécurité.

Solution : Spring Cloud Gateway (réactif, basé WebFlux — pas Tomcat/MVC) écoute sur 9090 et route par préfixe d'URL grâce à des predicates :

Route (Path predicate)URI cible
/api/users/**lb://service-utilisateurs
/api/events/**lb://service-evenements
/api/avis/**lb://service-avis
/api/reservations/**lb://service-reservation
/api/messages/** et /socket.io/** (WebSocket)lb://service-messaging

lb:// signifie load-balanced : la gateway demande l'adresse à Eureka puis répartit la charge entre les instances (client-side load balancing, Spring Cloud LoadBalancer). La gateway est aussi le point de contrôle sécurité (§5) et agrège les Swagger de tous les services (http://localhost:9090/swagger-ui.html, menu déroulant en haut à droite).

4.4 Comment les trois collaborent (la question piège classique)

Au démarrage : (1) le service contacte le Config Server → reçoit sa config, qui contient notamment l'adresse d'Eureka ; (2) il s'enregistre dans Eureka ; (3) quand une requête arrive, la Gateway matche la route, interroge Eureka pour résoudre lb://nom, valide le JWT et transmet la requête. D'où l'ordre de boot : config-server → eureka → keycloak → services → gateway (script run-all.ps1 qui attend le port de chacun avant de lancer le suivant).

5. Sécurité — Keycloak + OAuth2/JWT

5.1 Les acteurs

Keycloak héberge le realm gestion-evenements avec 3 rôles realm : ADMIN, ORGANISATEUR, PARTICIPANT, et un client public service-utilisateurs (grant password activé pour le login programmatique).

5.2 Le flux d'authentification (à savoir dérouler au tableau)

  1. Le frontend envoie email + mot de passe à POST /api/users/login (route publique de la gateway).
  2. service-utilisateurs relaie vers Keycloak (password grant sur /realms/gestion-evenements/protocol/openid-connect/token). Keycloak vérifie le mot de passe (c'est LUI qui stocke les mots de passe, pas notre base !) et renvoie un JWT signé RS256 contenant les rôles dans la claim realm_access.roles.
  3. Le frontend stocke le token (localStorage) et l'intercepteur Angular ajoute Authorization: Bearer … à chaque requête.
  4. La gateway (OAuth2 Resource Server) valide la signature du JWT grâce aux clés publiques de Keycloak (endpoint JWKS /protocol/openid-connect/certs) + l'issuer + l'expiration. Pas d'appel à Keycloak à chaque requête : la crypto asymétrique suffit (stateless).
  5. service-utilisateurs est LUI AUSSI resource server (défense en profondeur) et convertit realm_access.roles en autorités Spring ROLE_*.

5.3 Routes publiques vs protégées (SecurityConfig de la gateway)

Publiques : OPTIONS /** (préflight CORS), POST /api/users/register et /login, /socket.io/** (le navigateur ne peut pas mettre de header Authorization sur un WebSocket — le contrôle se fait au handshake côté messaging), actuator et Swagger. Tout le reste exige un JWT valide → sans token, 401 (démontrable dans Postman, requête n°4 de la collection).

5.4 Création de compte

register crée l'utilisateur dans Keycloak (API Admin REST : le service obtient d'abord un token admin sur le realm master avec le client admin-cli, puis POST /admin/realms/gestion-evenements/users, assigne le rôle) et un « profil miroir » dans MySQL (sans mot de passe — colonne supprimée, Keycloak est la seule source des mots de passe). Update/Delete synchronisent les deux.

6. Communication inter-services

6.1 Synchrone — OpenFeign (3 appels dans le projet)

À dire : @FeignClient(name = "service-evenements") — on donne le nom Eureka, pas une URL : Feign résout l'adresse via Eureka et fait du load balancing, comme la gateway. Feign génère l'implémentation HTTP à partir d'une simple interface annotée (programmation déclarative).

6.2 Asynchrone — RabbitMQ (événementiel)

Quand une réservation est créée, service-reservation publie un message JSON ReservationCreatedEvent (userId, titre, date) :

ÉlémentValeur
Exchange (topic)events.exchange
Routing keyreservation.created
Queue (durable)reservation.notifications
Consommateurservice-utilisateurs — @RabbitListener → log « 🔔 Notification : l'utilisateur #X a réservé… »
ConvertisseurJackson2JsonMessageConverter (JSON, pas de sérialisation Java)

Pourquoi asynchrone ici ? La notification n'est pas critique pour répondre au client : le publish est non bloquant et même entouré d'un try/catch — si RabbitMQ est éteint, la réservation réussit quand même (couplage faible, résilience). Comparaison à connaître : Feign = j'ai besoin de la réponse MAINTENANT (capacité) ; RabbitMQ = « fire and forget », le consommateur traitera quand il pourra, messages persistés dans la queue si le consommateur est down.

7. Persistance polyglotte (une BD par service — pourquoi ?)

Principe microservices : chaque service possède SA base, aucun service ne lit la base d'un autre (on passe par son API). Cela permet de choisir l'outil adapté :

  • MySQL (relationnel) pour utilisateurs, avis, messages : données structurées, relations, intégrité.
  • MongoDB (document) pour les événements : schéma flexible, embarqué via flapdoodle (zéro installation — pratique en démo).
  • H2 en mémoire pour les réservations : légère, create-drop (repart à zéro à chaque redémarrage), console visuelle sur http://localhost:8084/h2-console.

Hibernate/JPA fait le mapping objet-relationnel côté Spring (ddl-auto=update crée les tables), TypeORM (synchronize: true) l'équivalent côté NestJS.

8. Le frontend Angular 21

  • Standalone components + lazy loading : chaque page est chargée à la demande (loadComponent) — routes : /login, /users, /events, /chat.
  • Guards : authGuard (redirige vers /login si pas de token), guestGuard (l'inverse).
  • Intercepteur HTTP (auth-interceptor.ts) : ajoute automatiquement le Bearer token à chaque appel — le code métier n'en parle jamais.
  • Signals (réactivité moderne d'Angular) pour l'état : utilisateur courant, listes, formulaires.
  • Une seule URL d'API : environment.apiUrl = http://localhost:9090 → tout passe par la gateway.
  • Chat : socket.io-client se connecte à /socket.io via la gateway (proxy WebSocket) ; messages persistés en MySQL par le service NestJS.
  • Page Événements = la plus riche : liste les événements (Mongo), réserve (reservation), affiche/dépose les avis (avis) — règle métier : on ne peut noter que si on a réservé.

9. Docker & Monitoring

docker-compose.yml lance TOUT en un docker compose up --build : infra (mysql:8.4 — port hôte 3307 pour ne pas gêner le MySQL local —, rabbitmq:3.13 avec UI de management sur 15672, keycloak avec import du realm), puis config-server, eureka, les 5 services, la gateway, et le monitoring (Prometheus sur 9095 qui scrape /actuator/prometheus de chaque service, Grafana sur 3000 pour les dashboards).

Points à citer : healthchecks + depends_on: condition: service_healthy garantissent l'ordre de démarrage (l'équivalent Docker du Wait-Port de run-all.ps1) ; réseau bridge esprit-net où les conteneurs se joignent par nom (d'où les variables MYSQL_HOST=mysql, KEYCLOAK_HOST=keycloak injectées pour surcharger les défauts localhost) ; volume nommé mysql_data pour persister les données ; restart: unless-stopped.

10. Questions probables de la prof — avec les réponses

Q1. Pourquoi une architecture microservices plutôt qu'un monolithe ?

Déploiement et scalabilité indépendants (on peut scaler seulement service-evenements), technologies adaptées par service (Java, Node, MySQL, Mongo), isolation des pannes (si avis tombe, le reste vit), équipes autonomes. Coût : complexité d'infrastructure — c'est exactement ce que Config Server/Eureka/Gateway compensent.

Q2. Que se passe-t-il si Eureka tombe en marche ?

Les clients (gateway, Feign) gardent un cache local du registre : les appels continuent vers les adresses connues. Par contre, plus de nouveaux enregistrements ni de détection de pannes tant qu'il n'est pas revenu.

Q3. Et si le Config Server est éteint ?

Les services déjà démarrés ne sont pas affectés (la config est lue au boot). Mais un service qui (re)démarre échouera car il ne peut pas récupérer sa configuration — d'où son démarrage en premier.

Q4. Comment la gateway sait-elle où se trouve service-avis ?

Route Path=/api/avis/** → uri lb://service-avis : le préfixe lb:// déclenche Spring Cloud LoadBalancer qui interroge Eureka par nom logique et choisit une instance (round-robin si plusieurs).

Q5. Comment un JWT est-il validé ? La gateway appelle-t-elle Keycloak à chaque requête ?

Non. Le JWT est signé RS256 (asymétrique). La gateway télécharge une fois les clés publiques de Keycloak (JWKS) et vérifie localement signature + expiration + issuer. C'est stateless et performant. On peut décoder le token sur jwt.io pour montrer les claims (realm_access.roles, preferred_username, exp…).

Q6. Différence entre authentification et autorisation dans votre projet ?

Authentification = prouver qui je suis → Keycloak vérifie le mot de passe et émet le JWT. Autorisation = ce que j'ai le droit de faire → les rôles (ADMIN/ORGANISATEUR/PARTICIPANT) portés par le token, convertis en ROLE_* par Spring Security dans les services.

Q7. Pourquoi les mots de passe ne sont-ils pas dans votre base MySQL ?

Délégation à Keycloak (single source of truth, hashage/politiques gérés par un produit dédié). MySQL ne stocke qu'un profil miroir (nom, email, rôle, keycloakId) pour les jointures métier.

Q8. Feign vs RestTemplate/WebClient ?

Feign est déclaratif : on écrit une interface annotée, l'implémentation HTTP est générée. Intégré à Eureka + LoadBalancer (nom logique au lieu d'URL). Moins de code répétitif qu'un RestTemplate manuel.

Q9. Pourquoi RabbitMQ ici et pas un appel Feign ?

La notification n'exige pas de réponse immédiate : en asynchrone, la réservation répond vite même si le consommateur est lent ou éteint (le message attend dans la queue durable). Découplage : demain un service « emails » peut consommer le même exchange sans toucher au producteur. Le publish est même dans un try/catch : broker down ≠ réservation échouée.

Q10. Expliquez exchange / routing key / queue.

Le producteur publie dans un exchange (ici topic events.exchange) avec une routing key (reservation.created). L'exchange route vers les queues liées (binding) dont le pattern matche. La queue reservation.notifications stocke le message jusqu'à consommation par le @RabbitListener.

Q11. Pourquoi 3 types de bases de données différents ?

« Database per service » + persistance polyglotte : relationnel (MySQL) quand il faut intégrité/relations, document (MongoDB) pour un schéma flexible d'événements, H2 mémoire pour un service dont l'état peut être volatile en dev. Ça démontre l'indépendance des services : aucun schéma partagé.

Q12. Deux services peuvent-ils partager une base ?

Techniquement oui, mais c'est un anti-pattern microservices : couplage par le schéma. Ici chaque base appartient à UN service ; les autres passent par son API REST (ou par événements).

Q13. Comment le frontend attache-t-il le token ? Où est-il stocké ?

Dans le localStorage ; un HttpInterceptor Angular clone chaque requête sortante en ajoutant Authorization: Bearer token. Les guards bloquent la navigation si pas connecté.

Q14. Pourquoi la route /socket.io est-elle publique dans la gateway ?

L'API WebSocket du navigateur ne permet pas d'envoyer un header Authorization au handshake. Le contrôle d'accès est donc fait côté service-messaging au moment du handshake, et la gateway se contente de proxyfier le WebSocket.

Q15. Que voit-on sur http://localhost:8761 ?

Le dashboard Eureka : la liste des instances enregistrées (SERVICE-UTILISATEURS, SERVICE-EVENEMENTS, SERVICE-AVIS, SERVICE-RESERVATION, SERVICE-MESSAGING, API-GATEWAY) avec statut UP — la preuve vivante de la découverte de services.

Q16. Comment Swagger fonctionne-t-il à travers la gateway ?

Chaque service expose sa doc OpenAPI sous sa propre route (ex. /api/avis/v3/api-docs). La gateway déclare ces URLs dans springdoc.swagger-ui.urls[…] : une seule UI (:9090/swagger-ui.html) avec un menu déroulant pour naviguer entre TOUTES les APIs — le tout récupéré à travers la gateway elle-même.

Q17. Local vs Docker : qu'est-ce qui change ?

Rien dans le code ! Les configs utilisent ${VAR:localhost} : en local les défauts s'appliquent ; dans Docker, compose injecte MYSQL_HOST=mysql, EUREKA_HOST=eureka-server, KEYCLOAK_HOST=keycloak… et les conteneurs se résolvent par nom sur le réseau bridge. Les healthchecks remplacent l'attente de ports du script local.

Q18. À quoi servent Prometheus et Grafana ?

Spring Boot Actuator expose des métriques au format Prometheus (/actuator/prometheus) : requêtes/s, latences, mémoire JVM… Prometheus les scrape périodiquement et les stocke ; Grafana les visualise en dashboards. C'est l'observabilité, indispensable quand on a 7 services.

Q19. Que se passe-t-il si service-reservation est down quand on consulte un profil ?

GET /api/users/{id}/reservations dégrade proprement : l'appel Feign échoue mais le service renvoie le profil avec une liste vide/erreur signalée au lieu de tout casser (tolérance aux pannes).

Q20. Pourquoi votre Keycloak est sur 8089 et pas 8080 ?

Spécificité de la machine : Oracle Database occupe déjà le port 8080. Le port est centralisé dans la config (placeholder KEYCLOAK_BASE_URL), donc un seul endroit à changer — et dans Docker il repasse en 8080 interne via KEYCLOAK_HOST=keycloak.

11. Scénario de démonstration conseillé (10 min)

  1. ./run-all.ps1 puis cd frontend; npm start — montrer l'ordre de démarrage.
  2. Ouvrir Eureka (8761) : tous les services UP.
  3. Ouvrir Keycloak (8089, admin/admin) : realm, rôles, utilisateurs.
  4. Frontend : register → montrer l'utilisateur créé DANS Keycloak ET dans MySQL.
  5. Login → décoder le JWT sur jwt.io (rôles, expiration).
  6. Créer un événement, le réserver → montrer le log « 🔔 [RabbitMQ] » dans la console de service-utilisateurs (si RabbitMQ lancé).
  7. Laisser un avis (possible seulement après réservation) → moyenne mise à jour.
  8. Chat à deux navigateurs (temps réel Socket.IO).
  9. Postman : appel sans token → 401 (sécurité effective).
  10. Swagger agrégé (9090/swagger-ui.html) et, si demandé, H2 console (8084/h2-console) + RabbitMQ UI (15672).

Pièges connus de VOTRE machine (à ne pas oublier le jour J) : Keycloak = port 8089 (8080 = Oracle) · mot de passe MySQL root = vide · ne jamais faire « Discard changes » sur les fichiers de config (ça a déjà annulé les corrections) · RabbitMQ doit être lancé (Docker) pour la démo notification, sinon tout marche mais sans le log 🔔.

Phrase de synthèse à retenir : « Le client n'a qu'une porte d'entrée (la gateway), les services n'ont qu'une source de configuration (le config server), et personne ne connaît l'adresse de personne : tout le monde se trouve par son nom grâce à Eureka. La sécurité est déléguée à Keycloak via des JWT vérifiés cryptographiquement, les échanges critiques sont synchrones (Feign), les non-critiques asynchrones (RabbitMQ), et chaque service est maître de sa propre base de données. »
